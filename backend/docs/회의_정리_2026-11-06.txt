2. 팀 전체가 같이 정해야 할 것
==================================================

① 모집 완료(R11) 정책
- 모집이 언제 "완료"인지 결정 필요
- 현재: 정원이 차면 CLOSED, COMPLETED는 작성자 탈퇴 시에만 설정
- 별도 완료 처리 API를 둘지, 완료 시 팀 프로젝트(MATCHED) 경험을 자동 생성할지 결정 필요
- B의 활동 점수/수료 연동이 이 결정에 걸려 있음

② 요구사항 정의서와 SQL의 값 불일치
- 모집 상태: 정의서 RECRUITING/COMPLETED, 현재 구현(SQL) OPEN/CLOSED/COMPLETED
- 프로젝트 종류: 정의서 CLUB_PROJECT/CLUB_MEMBER_TEAM/SELF, SQL OFFICIAL/MATCHED/PERSONAL
- 현재는 SQL 기준으로 구현. 프론트와 B가 쓰는 값이므로 어느 쪽으로 통일할지 결정 필요

③ 알림 연동 방식
- 호출 시그니처 합의, 트랜잭션 커밋 이후 호출 여부 결정
- 알림 필요 지점: 지원 접수, 제안 접수, 수락/거절, 마감/삭제로 거절된 건, 탈퇴로 취소된 건(X3)
- audit_logs 기록 서비스 인터페이스도 함께 합의

④ 가입 코드 최초 설정 API (B 구현)
- 이 API가 없으면 일반 회원이 가입 코드 인증을 통과할 수 없어 가입 흐름 전체가 막힘
- 구현 시점 결정 필요

⑤ users.completed 의미
- 프로필 완성 표시인지, 동아리 수료 여부인지 확인 필요
- 정의서 기준으로는 수료 여부로 보이나 B 쪽 이해와 맞는지 확인

⑥ 임베딩 갱신 방식
- 프로필/모집글 수정 시 embedding_stale = TRUE 로 표시됨
- B가 TRUE 인 행을 읽어 재계산 후 FALSE 로 되돌리는 방식에 동의하는지 확인

⑦ 정책 결정 (보안/개인정보)
- 가입 코드 시도 제한: 현재 제한 없음(무차별 대입 가능). 추천: 회원당 5회 실패 시 15분 잠금
  (서버가 여러 대면 DB 방식으로 변경)
- 탈퇴 회원 개인정보: 현재 계속 보관, 재가입 불가.
  선택: 그대로 유지 / 일정 기간 후 이름, 이메일 삭제
- 오픈채팅 링크 공개 범위: 작성자/확정 팀원/운영진에게만 공개로 정함.
  정의서에는 "상세에 항상 공개"로 되어 있어 서로 다름 -> 공개 범위 확정 및 정의서 수정 필요

⑧ 임의로 정한 설정값 재확인
- 정원 상한 50명
- 모집 역할 10개
- 직접 입력 기술 5개
- 프로젝트 50개
- 공개 프로젝트 최신순 3개
- 검색: 같은 분류 안은 OR, 분류끼리 AND

⑨ 환경/도구
- 운영 PostgreSQL 버전, Node 최소 버전(engines) 미정
- ESLint/Prettier, Swagger, rate limit 도입 여부 (Swagger는 프론트 협업에 영향 큼)
- Google OAuth 키를 누가 발급해서 공유할지
- 개발 의존성 취약점: npm audit fix --force 가 필요해서 보류 중

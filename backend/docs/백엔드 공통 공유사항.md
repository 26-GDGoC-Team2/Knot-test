## 2. 코드 규칙

- Controller - Service - Repository 계층을 분리. 비즈니스 로직은 반드시 Service 에 작성, Controller 는 요청/응답만 담당.
- 모든 REST 응답은 CommonResponse 사용. 실패는 응답을 직접 만들지 말고 예외를 던질 것.
- 모든 비즈니스 로직에 예외 처리와 null/엣지 케이스 검증 포함. 한글 주석은 짧고 간결하게.
- 폴더: src/modules/{모듈}/ 아래 controller, service, repository 파일. 공통 코드는 src/common/.
- 새 로직에는 *.spec.ts 테스트를 함께 작성. DB 는 가짜(mock)로 대체하는 방식은 modules/users/user.service.spec.ts 를 참고.

## 3. DB 접근과 트랜잭션

- common/database.service.ts 의 DatabaseService 를 주입받아 사용 (전역 모듈이라 import 불필요).
- Repository 는 SQL 만 담당하고, 모든 메서드가 마지막 인자로 db: Queryable 을 받도록 작성 (생략 시 풀 사용). 트랜잭션 client 와 풀 모두 Queryable 로 받을 수 있음.
- 트랜잭션은 Service 에서 database.transaction(async (tx) => { ... }) 로 열고, 안의 모든 Repository 호출에 tx 를 넘길 것. 예외가 나면 자동 롤백.
- 동시성이 있는 로직(정원, 수락)은 트랜잭션 안에서 SELECT ... FOR UPDATE 로 행 잠금.
- unique 위반 확인은 isUniqueViolation(e) 사용.

```ts
const result = await this.database.transaction(async (tx) => {
  const role = await this.repo.findRoleForUpdate(recruitmentId, roleId, tx); // FOR UPDATE
  await this.repo.accept(applicationId, tx);
  return this.repo.increaseConfirmed(recruitmentId, roleId, tx);
});
```

| verified-guard.ts | 가입 코드를 통과하지 않은 회원은 기본적으로 모든 API 가 403(JOIN_CODE_REQUIRED). 미인증 회원도 써야 하는 API 에만 @AllowUnverified() 를 붙임(B 담당 API 는 대부분 붙일 필요 없음). |

| pagination.ts | 목록 쿼리는 PageRequest 로 받고 PageResponse.of(items, total, req) 로 반환. page 기본 1, size 기본 20 (최대 100). 정렬은 resolveSort({API필드: DB컬럼}, 기본값) 허용 목록만 허용. |
| join-code-crypto.ts | 가입 코드 암호화. encryptJoinCode(plain) / decryptJoinCode(enc). join_codes.code_enc 에 저장하는 형식이므로 반드시 이 함수를 사용(직접 암호화 금지). JOIN_CODE_ENC_KEY 환경 변수 필요. |
| health.controller.ts | GET /health 공개 경로 (이미 있음). |

## 5. 인증 / 현재 사용자 / 탈퇴 회원

- 모든 경로는 기본적으로 인증 필요. 컨트롤러에서 req.user 로 {id, role, verified} 를 사용 (id = users.id).
- 공개 경로는 config/auth.config.ts 의 PUBLIC_ROUTES 에만 있음(로그인 관련 + /health). B 담당 API 는 추가하지 말 것.
- 탈퇴 회원: users 행은 삭제하지 않고 status = WITHDRAWN. 회원 정보가 응답에 나가는 모든 곳(작성자, 팀원, 부원 목록 등)은 modules/users/user.dto.ts 의 toPublicUser() 로 변환해서 "탈퇴한 회원"으로 표시할 것. 이메일 등 식별 정보는 응답에 넣지 말 것.
- Access 토큰은 30분이라 탈퇴 직후 최대 30분은 기존 토큰으로 접근 가능. 탈퇴 여부가 중요한 API(수료 지정, 팀원 확정 등)는 users.status 를 직접 확인.
- 탈퇴 시 처리(구현됨): 작성한 OPEN 모집글 -> COMPLETED, 대기(PENDING) 지원/제안 -> CANCELED, Refresh 토큰 전부 폐기. 마지막 운영진은 탈퇴 거부(403 LAST_ADMIN).
- 운영진 지정/해제 API(B 담당)도 마지막 운영진을 해제할 수 없도록 같은 규칙을 적용하고, 시작 시 lockAdminChanges(tx) 를 호출할 것. 에러는 ErrorCode.LAST_ADMIN 사용.

## 6. DB / 마이그레이션

- 현재 마이그레이션 2개: 1793664000000_init-a-tables.sql ([A] 테이블: 회원/인증, 프로필, 선택 목록, 프로젝트 경험, 모집글, 지원/제안)과 1793664000001_seed-master-data.sql (선택 목록 기본 데이터). 임시 PostgreSQL 17 에서 up/down/up 과 통합 테스트로 검증 완료. 운영 DB 는 미검증.
- 시드(1793664000001): 희망 역할 6개(PM, 디자인, FE, BE, AI, 앱), 기술 18개, 관심 분야 11개. 요구사항 정의서의 "예시" 목록이라 최종이 아님 - 추가/변경은 새 마이그레이션으로. 가짜(테스트) 데이터는 시드에 넣지 않음.
- 모집글 소프트 삭제: recruitments.deleted_at 이 있으면 삭제된 글. 모집글을 조회하는 모든 쿼리(B 의 아카이브, 알림, 활동 점수 등 포함)에 "deleted_at IS NULL" 조건을 넣을 것. 지원/제안 이력은 보존됨.
- 지원/제안 중복 규칙: 지원(APPLY)은 모집글당 대기(PENDING) 1건(역할 무관), 제안(PROPOSE)은 같은 모집글에서 같은 대상자에게 대기 1건. 거절/취소된 뒤에는 다시 가능. 위반하면 unique 위반(isUniqueViolation)이므로 409 로 변환.
- applications.message: DB 는 200자까지만 막고(체크 제약), 실제 제한(기본 50자)은 서비스 설정값으로 검사.
- 필터/조인용 인덱스가 추가됨(역할/기술/관심 분야 역방향, 모집글 상태/작성자는 삭제되지 않은 글만, 지원서의 모집글 기준 등). [B] 테이블 쿼리가 느리면 A 와 상의.
- [B] 테이블(알림, 푸시 구독, 참여 기록, 활동 점수, 가입 코드 이력, 권한 변경 이력, 감사 로그, 아카이브, 공모전)은 B 담당이 별도 마이그레이션 파일로 추가: `npm run migrate:create -- 이름`
- [B] 테이블이 참조할 기존 테이블/타입: users, join_codes, recruitments, project_type(enum). 이 이름과 enum 값을 바꿔야 하면 변경 전 A 와 상의.
- users.completed (수료 여부)는 B 가 쓰고 A 가 읽음. 수정은 운영진 수료 지정 API 에서만.
- 가입 코드 쓰기(최초 설정, 변경)는 B 담당 운영진 모듈이 구현. 인증 모듈은 join_codes 를 읽기만 함. 코드가 없으면 일반 회원의 가입 코드 인증은 모두 실패하므로, 최초 운영진이 가장 먼저 코드를 설정해야 함. 변경 시 join_codes 와 join_code_histories 를 하나의 트랜잭션으로 처리하고, 새 코드 저장 시 이전 코드의 active 를 false 로 바꿀 것(active=true 는 항상 1개).
- 활동 점수 기준표(대외활동 20/10, 입상 20/15/10, 논문 KCI 20 / SCI 40 등)는 하드코딩하지 말고 설정 테이블 또는 설정 파일로 분리.

- 프로필 통합 테스트: `TEST_DATABASE_URL=<주소> npx jest src/modules/profile/profile.db.spec.ts`

## 8. 모집/지원 모듈

| API | 설명 |
|---|---|
| POST /recruitments | 모집글 작성. 운영진이 아닌 일반 회원도 가능. 작성자가 맡을 역할(authorRoleId)을 함께 보냄 |
| GET /recruitments, GET /recruitments/:id | 목록(status=OPEN/DONE, roleIds, skillIds, interestIds, q, mine, 페이지네이션)과 상세 |
| PUT /recruitments/:id | 수정. 작성자 또는 운영진, 모집 중(OPEN)일 때만 |
| POST /recruitments/:id/close, DELETE /recruitments/:id | 수동 마감(CLOSED)과 소프트 삭제. 작성자 또는 운영진. 둘 다 대기 중 지원/제안을 일괄 거절 |
| POST /recruitments/:id/applications, /proposals | 지원(회원 -> 작성자)과 제안(작성자 -> 부원). 한 줄 메시지 최대 50자 |
| GET /recruitments/:id/applications | 모집글의 지원/제안 목록 (작성자 또는 운영진) |
| GET /applications?box=sent\|received | 내가 보낸/받은 지원·제안 목록 |
| POST /applications/:id/accept \| reject \| cancel | 수락/거절은 받은 사람만, 취소는 보낸 사람만. 운영진도 남의 지원은 수락 불가 |

- 정원 규칙: recruitment_roles.capacity 는 작성자를 포함한 인원, confirmed_count 도 작성자를 포함함. 작성자는 모집글 작성 시 recruitment_members 에 자동 등록되어 선택한 역할이 1/N 으로 시작. 참여 기록/활동 점수에서 팀원을 셀 때 작성자가 포함된다는 점에 유의.
- 상태: 수락으로 모든 역할의 정원이 차면 자동으로 CLOSED. 수동 마감도 CLOSED. COMPLETED 는 현재 작성자 탈퇴 시에만 설정됨(완료 처리 API 와 MATCHED 경험 자동 생성은 보류 중이라 B 의 수료/활동 점수 연동 시점은 협의 필요). 완료 탭 = CLOSED + COMPLETED.
- 일괄 거절: 마감/삭제/자동 마감/정원이 찬 역할의 남은 대기 건은 REJECTED, 팀원으로 확정된 회원의 같은 모집글 내 다른 대기 건은 CANCELED, 역할 삭제 시 그 역할의 대기 건은 REJECTED. 모두 같은 트랜잭션 안에서 처리됨.
- 동시성: 수락은 모집글 행 -> 역할 행 -> 지원 행 순서로 FOR UPDATE 잠금. B 가 recruitments / recruitment_roles / applications 를 함께 수정하는 트랜잭션을 만들 때는 반드시 이 순서를 지킬 것(교착 방지). 지원/제안 생성은 모집글을 FOR SHARE 로 잠금.
- 오픈채팅 링크(open_chat_url)는 작성자, 확정 팀원, 운영진에게만 응답에 포함됨. 다른 응답(알림, 아카이브 등)에서 링크를 내보낼 때도 같은 기준을 지킬 것.
- 권한 판단은 JWT 의 role 이 아니라 DB 의 현재 role/status 를 사용함(운영진 해제 직후 30분 지연 방지). B 의 운영진 전용 로직도 중요한 변경에는 DB 값을 확인할 것.
- 임베딩: 모집글 수정 시 recruitments.embedding_stale = TRUE 로 표시됨(프로필과 동일한 방식).
- 알림 연동 자리(미연동, 코드에 TODO(C4) 주석): 지원 접수(작성자에게), 제안 접수(대상자에게), 수락/거절(보낸 사람에게), 마감/삭제/자동 마감으로 거절된 대기 건(해당 지원자에게). 호출 방식이 합의되면 각 트랜잭션 커밋 이후에 호출하도록 추가함.
- 프로젝트 파일 주의: src/modules/recruitment/ 에 있던 0바이트 빈 파일 recruitment.service, recruitment.controller(확장자 없음)는 jest 모듈 해석을 방해해서 삭제함. src/common/audit-log, src/modules/recommendation/score-calculator 도 확장자 없는 0바이트 파일인데, 같은 이름의 .ts 파일을 만들면 import 가 이 빈 파일을 먼저 잡으므로 만들기 전에 삭제할 것.
- 테스트: 전체 243개 통과 (단위 + 실제 DB 통합). 모집 통합 테스트(정원 동시 수락, 자동 마감, 일괄 거절, 권한 포함): `TEST_DATABASE_URL=<주소> npx jest src/modules/recruitment/recruitment.db.spec.ts`. 통합 테스트 파일은 병렬로 실행되므로 DB 전체 개수를 세는 단언을 쓰지 말고 자기 접두어 데이터만 검사할 것.

## 10. 실행 방법

```bash
cd backend && npm install
copy .env.example .env   # 아래 값을 채움
npm run build
npm test
npm run start:dev       # 개발 서버 (반드시 backend/ 폴더에서 실행)
npm run migrate:up      # DATABASE_URL 필요
```

개발/검증용 임시 DB (PostgreSQL 설치 없이 사용, 운영 DB 와 무관):

```bash
node scripts/dev-db.mjs setup   # 최초 1회: PostgreSQL 패키지 설치 (경로에 한글이 있을 때만 필요, 그 외에는 npm install 로 충분)
npm run db:dev                  # DB 기동 (Ctrl+C 로 종료), 접속 주소: node scripts/dev-db.mjs url
npm run db:dev:stop             # DB 종료
npm run db:dev:reset            # 종료된 상태에서 데이터 전부 삭제 (가짜 데이터 포함)
```

- 접속 주소는 `postgres://knot:knot_dev_only@127.0.0.1:54329/knot_dev` (127.0.0.1 에서만 접속 가능한 로컬 전용 값). DATABASE_URL 에 넣어 사용.
- 주의: Windows 에서 프로젝트/사용자 폴더 경로에 한글이 있으면 PostgreSQL 이 초기화에 실패함. 이 경우 스크립트가 C:\Users\Public\ 아래 영문 경로를 대신 사용함.
- 임시 DB 를 처음 쓸 때는 기동 후 npm run migrate:up 으로 테이블과 시드를 만들 것 (DATABASE_URL 필요).
- 실제 DB 통합 테스트: `TEST_DATABASE_URL=<위 주소> npx jest` (src/integration.db.spec.ts 는 localhost 가 아니거나 ADMIN 회원이 이미 있는 DB 에서는 실행을 거부함. 모든 통합 테스트는 만든 데이터를 끝나면 삭제하고, 변수가 없으면 건너뜀).
- .env 필수 항목: JWT_ACCESS_SECRET, JWT_REFRESH_SECRET (각 32자 이상, 서로 다르게), GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET / GOOGLE_REDIRECT_URI, FRONTEND_URL, JOIN_CODE_ENC_KEY, DATABASE_URL. 선택: FIRST_ADMIN_EMAIL, COOKIE_SECURE, COOKIE_SAMESITE.
- secret 생성: `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`
- .env 는 커밋하지 말 것. 필수 값이 없으면 서버가 시작 시 실패함.

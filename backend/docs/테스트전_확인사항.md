# 실제 테스트 전 확인사항

A·B 코드를 합친 뒤 실제(배포) 환경에서 테스트하기 전에 준비할 것들입니다.
B 담당 모듈이 모두 끝났다는 가정입니다. (작성일 2026-11-08)

## 0. 먼저 정할 것 (B·팀 협의)
- [ ] 도메인 방식: 프론트와 백엔드를 같은 도메인의 하위 주소로 둘지 (예: `app.○○.com`, `api.○○.com`)
  - 다른 도메인이면 iPhone/Safari가 로그인 쿠키를 막아 로그인이 유지되지 않을 수 있음
- [ ] B 모듈이 필요로 하는 환경변수 목록 (웹 푸시 VAPID 키, 공모전 수집 등)
  - 원격(`knot-backend`) 확인 결과 B 코드가 새로 읽는 값은 `AI_SERVER_URL` 하나 (추천 모듈). 값과 주소를 B에게 확인
  - 웹 푸시·공모전 수집 코드는 원격에 아직 없음 (7장 참고)
- [ ] 마이그레이션 번호: **충돌 확인됨** — 원격 B `...03_add-notification-types`와 내 A `...03_frontend-requests`가 같은 번호 (7장 참고)
- [ ] 선택 목록(기술·관심 분야) 기준을 서버로 통일할지
- [ ] 프론트 모집글 작성 화면에 팀 채팅방 링크 입력칸 추가 여부 (서버는 필수)
- [ ] 마이그레이션 운영 규칙: 정식 경로는 `backend/migrations/` 하나만 사용, `B담당/migrations/` 사본은 수정하지 않고 정리
  - 이미 적용된 파일은 수정하지 않고 새 마이그레이션 파일로 추가
  - 번호 충돌 방지: A는 홀수, B는 짝수 (현재 B `...02`, A `...03`)
  - FK 방향: B는 A 테이블(`users` 등)을 참조해도 되지만, A는 B 테이블을 직접 참조하지 않음
  - 상대 담당 테이블의 컬럼 변경은 상대 동의 후에만
- [ ] AI팀 `activity_count` 정의 확인 후 담당 확정 (A 제안: 프로필 조회 시 `COUNT`로 계산해 A가 제공)
  - 확인할 것: 팀 참여 횟수인지 / 완료된 프로젝트 수인지, `PERSONAL` 경험 포함 여부, 지원 횟수 포함 여부
  - 점수 개념(B의 `activity_scores`)이라면 `activity_score` 필드로 분리해 B가 제공
- [ ] 팀원 참여 시험 방식: 배포(Vercel+호스팅) / 내 PC 터널(`cloudflared`·`ngrok`, https 주소 필요)
  - 같은 와이파이의 사설 IP(`192.168.x.x`)는 Google 로그인 리디렉션이 허용되지 않아 사용 불가

## 1. 새로 만들 값 (호스팅 환경변수에 직접 입력, GitHub·채팅에 올리지 않기)
| 변수 | 만드는 방법 |
|---|---|
| `JWT_ACCESS_SECRET` | `node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"` |
| `JWT_REFRESH_SECRET` | 위 명령을 다시 실행 (Access와 서로 다른 값) |
| `JOIN_CODE_ENC_KEY` | `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` |
| `DATABASE_URL` | 아래 "DB는 2개로 분리"에서 만든 주소 (SSL 요구 시 끝에 `?sslmode=require`) |

> 개발용 키를 운영에 재사용하지 않는다. `JOIN_CODE_ENC_KEY`를 바꾸면 기존 가입 코드를 복호화할 수 없다.

### DB는 2개로 분리 (시험용 / 실제 배포용)
설치할 도구는 없다. Neon(neon.tech) 등에 가입하고 웹에서 만든다. 만들면 나오는 Connection string이 `DATABASE_URL`이다.

| DB | 이름 예시 | 용도 |
|---|---|---|
| 시험용 | `knot-test` | 내 PC에서 백엔드를 연결해 시험, 첫 배포 후 로그인·모집글 흐름 시험. 시험 계정·모집글을 마음껏 만들고 지워도 됨 |
| 실제 배포용 | `knot-prod` | 정식 배포에 연결. 마이그레이션만 적용한 깨끗한 상태로 시작 |

- 분리 방법: Neon 프로젝트 2개 (가장 단순). 무료 플랜의 프로젝트 개수 제한이 있으면 한 프로젝트의 브랜치 2개(`main`, `test`)로 나눔
- 주소·비밀번호는 어느 DB 것인지 이름을 붙여 따로 보관
- `export DATABASE_URL`을 하기 전에 시험용인지 배포용인지 반드시 확인 (시험 명령을 배포용에 실행하면 시험 데이터가 섞임)
- 자동 테스트(`jest`)는 이 DB들에 돌리지 않는다. 개발용 임시 DB(`npm run db:dev`)에서만 실행
- 시험이 끝나면 `backend/.env`의 `DATABASE_URL`을 개발용 임시 DB 주소로 되돌린다
- 업체 무료 플랜의 저장 용량·일시 중지·백업 기간을 가입 화면에서 확인 (실제 부원이 쓰는 DB는 데이터가 유지되는 요금제인지 확인)

## 2. 환경변수 전체 (백엔드)
| 변수 | 값 |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` | 호스팅이 지정 (대부분 자동) |
| `DATABASE_URL` | 배포 환경에는 **실제 배포용** DB 주소 (시험용 주소는 내 PC에서만 사용) |
| `FRONTEND_URL` | `https://knot-web-ten.vercel.app` (끝에 `/` 없이) |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | 기존 값 사용 가능 |
| `GOOGLE_REDIRECT_URI` | `<백엔드 주소>/auth/google/callback` |
| `COOKIE_SAMESITE` / `COOKIE_SECURE` | `none` / `true` (같은 도메인 하위 주소면 기본값 가능) |
| `JWT_ACCESS_EXPIRES_IN` / `JWT_REFRESH_EXPIRES_IN` | `30m` / `14d` |
| `FIRST_ADMIN_EMAIL` | 실제 최초 운영진 이메일 (이 이메일로 처음 가입하면 운영진) |

- `COOKIE_SAMESITE=none`은 `COOKIE_SECURE=true`와 반드시 함께 설정 (아니면 서버 시작 시 에러). https에서만 동작
- `FIRST_ADMIN_EMAIL` 부여는 운영진이 한 명도 없을 때 1회뿐이므로, 공유 DB에서는 해당 이메일로 가장 먼저 로그인
- `VITE_API_URL`은 프론트 빌드 때 값이 박히므로 바꾸면 재배포 필요
- 시험용/배포용 환경마다 `FRONTEND_URL`, `GOOGLE_REDIRECT_URI`, Google Console 리디렉션 URI를 같은 주소로 맞추기 (터널 주소는 실행할 때마다 바뀔 수 있음)

## 3. 배포 순서
DB는 배포 전에 먼저 만든다 (배포한 백엔드가 시작할 때 DB 주소가 필요). 순서: DB 생성 → 마이그레이션 → 배포.

1. [ ] **시험용 DB**(`knot-test`) 생성 → 마이그레이션 → 내 PC 백엔드를 연결해 시험
   ```bash
   cd backend
   export DATABASE_URL="<시험용 DB 주소>"
   npm run migrate:up      # 빈 DB에서 A+B 마이그레이션이 끝까지 적용되는지 확인
   npm run start:dev       # 이 DB로 백엔드 실행 → 프론트(localhost:5173)에서 흐름 시험
   ```
2. [ ] 비밀키 3개 생성
3. [ ] 백엔드 배포: GitHub `knot-backend` 연결
   - 빌드 명령: `npm install && npm run build`
   - 시작 명령: `node dist/main`
   - 위 환경변수 입력 → 배포 후 나오는 HTTPS 주소 확인
   - 처음에는 시험용 DB 주소로 배포해 시험하고, 정식 오픈 직전에 실제 배포용 주소로 교체
4. [ ] Google Cloud Console → OAuth 클라이언트 → 승인된 리디렉션 URI에 `<백엔드 주소>/auth/google/callback` 추가 (`GOOGLE_REDIRECT_URI`와 정확히 동일)
   - Google OAuth 동의 화면이 "테스트" 상태면 시험에 참여할 팀원 이메일을 **테스트 사용자**에 등록 (없으면 로그인 차단)
5. [ ] **실제 배포용 DB**(`knot-prod`) 생성 → 마이그레이션 (정식 오픈 전)
   ```bash
   cd backend
   export DATABASE_URL="<실제 배포용 DB 주소>"   # 시험용이 아닌지 한 번 더 확인
   npm run migrate:up
   ```
6. [ ] Vercel 환경변수 `VITE_API_URL=<백엔드 주소>` 추가 후 재배포
7. [ ] 프론트 연동 코드를 프론트 레포(`knot-web`)에 PR로 반영 (현재는 내 PC 사본에만 있음)
8. [ ] 정식 오픈: 배포 환경의 `DATABASE_URL`을 실제 배포용으로 교체 → 첫 로그인(`FIRST_ADMIN_EMAIL`)으로 운영진 확인 → 가입 코드 발급

## 7. 원격 저장소(`knot-backend`) 통합 점검 결과 (2026-11-09)
B가 올린 `main`(커밋 `0fea1a1`)을 별도 폴더에 받아 점검했습니다. 내 작업 폴더는 변경하지 않았습니다.

**시험 결과 (원격 코드 단독)**
- `npm run build` 통과
- 마이그레이션 `0000`~`0008` 9개가 빈 DB에서 끝까지 적용됨
- `jest` 16개 스위트 · 243개 테스트 전체 통과 (DB 테스트 포함)
- 서버 부팅 정상, `/health` 응답 확인, B 경로(`/activity`, `/archive`, `/admin`, `/notifications`, `/recommendations`)는 인증 없이 401
- 단, B 모듈(activity·archive·recommendation·notifications)은 단위 테스트가 거의 없어 위 통과가 B 동작을 보증하지는 않음

**통합 전 해결할 것**
- [ ] **A 최신 작업이 원격에 없음**: 원격의 A 코드는 내 이전 커밋(`12ef038`) 기준. `reject_reason`, `team_chat_url`(팀 채팅방 링크), 정원 정산, 프로필 정리(`5a6782b`)가 빠져 있음
- [ ] **마이그레이션 번호 충돌**: 원격 `...03_add-notification-types` ↔ 내 `...03_frontend-requests`
  - 해결안: 내 파일을 새 번호(`...09_frontend-requests`)로 변경. 이미 내 개발 DB에 적용돼 있으므로 번호 변경 후 `npm run db:dev:reset`으로 개발 DB를 다시 만들기
  - 새 번호는 B와 겹치지 않게 협의 (B가 이어서 `...09` 이상을 쓰는지 확인)
- [ ] 같은 A 파일(recruitment·application·user·profile)을 양쪽이 수정함: `git merge` 시 충돌 예상. 원격 `main`을 기준으로 내 A 변경을 다시 적용하는 방식을 권장
- [ ] 통합 후 B 알림 로직이 내 A 신규 기능(모집 마감 구분, 정원 정산)과 맞는지 확인 (알림 타입 `RECRUITMENT_CLOSED`, `RECRUITMENT_COMPLETED` 등)

**통합 결과 (로컬 `integration` 브랜치, 2026-11-09)**
- 원격 `main` 기준으로 내 A 변경(`reject_reason`, 팀 채팅방 링크, 정원 정산, 프로필 정리)을 적용, 마이그레이션 `...03_frontend-requests`를 `...09_frontend-requests`로 변경

## 8. 알려진 한계 (연동 시험에서 확인)
- 모집글 목록 조회는 글마다 상세를 다시 요청함 (목록 응답에 설명·기술이 없음)
- 서버 검증 오류 메시지가 항목별로 내려오지 않음 ("입력값이 올바르지 않습니다")
- 서버에 없는 기술은 모집글 필수/우대 기술에 저장되지 않음
- "매칭 화면을 봤는지"는 서버에 없고 브라우저에만 기억됨
